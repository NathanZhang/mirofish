# MiroFish 应用场景分析报告

日期：2026 年 10 月 27 日。分析对象为本仓库 `feat/graphiti-local` 分支 `30cc3fa` 的本地 Graphiti 版本，面向应用选型、试点设计和后续开发决策。

## 结论与建议

当前版本最适合定位为**材料驱动的多角色方案预演与争议发现系统**：给定角色、关系、规则和背景，观察模拟参与者如何理解、质疑与回应，再把讨论整理成带来源的问题清单、FAQ 缺口和改进建议。

除已验证的共享阅读室场景外，优先试点三个方向：**产品与服务规则发布前评审、企业流程变更沟通、客户服务争议与公告演练**。它们主要依赖文字规则、明确角色和可追溯讨论，通常可以先通过材料、配置和人工审核开展小规模试点，无需先改造核心引擎。

培训复盘、社区平台规则设计、园区或项目多方协商、群像创作也有适配空间。供应链场景应先限定为异常沟通与责任交接；库存、运力、交期概率等定量问题需要另外的计算与业务数据。

这些是基于当前能力的应用判断，不是已经完成的行业效果验证。已有业务实测仍是共享阅读室案例：8 个 Agent、双平台各 3 轮、36 条写回动作，其中 14 条初始配置动作、22 条自主动作，包含 12 条自主发言。该实测证明主链路可运行，不证明能够预测真实购买、流失或民意比例。参见[案例与功能说明](MiroFish案例与功能说明.md)。

## 1 能力基础与研究依据

### 1.1 当前版本已经具备什么

| 已有能力 | 对场景选型的意义 | 边界 |
|---|---|---|
| 文件解析、本体与关系图 | 能把文档中的角色、职责、约束和冲突关系组织起来 | 抽取会出现主体重复或事实扩展，需审核 |
| 自动人设和平台配置 | 能构造多种立场，开展小规模讨论 | 自动人设没有自动获得真实用户代表性 |
| Twitter/Reddit 型本地模拟 | 能观察发帖、评论、回应和点赞等互动 | 是社交讨论环境，不是企业工单、库存或物理世界引擎 |
| 动作数据库确认与记忆写回 | 能把模拟过程作为分析来源，而不只改写输入材料 | 实际落库不等于内容真实 |
| 图谱检索、报告和来源附录 | 适合输出争议、疑问、条件性支持与建议 | 报告解释仍可能超过证据强度 |
| 环境关闭前的 Agent 访谈 | 可以追问角色对规则的理解 | 环境关闭后不能靠旧报告自动恢复访谈 |
| 本地 Graphiti、Neo4j 与 CPU 向量 | 便于在本机组织内部材料和证据 | 本地部署不自动完成去标识、授权及访问权限管理 |
| 持久化 job、outbox 和水位 | 可以检查是否完整摄入，解释失败位置 | 不代表所有后台任务都可以重启续跑 |

当前最有价值的产物是“需要人工检查的问题和交互证据”。这些产物与当前软件能力之间有直接对应关系，比直接承诺数值预测更适合本阶段。

### 1.2 相关研究支持哪些方向

OASIS 研究构建了包含社交网络、帖子、动作和推荐机制的社交模拟环境，用于考察信息传播等群体现象。这支持把本项目用于讨论与互动结构研究，但论文中的规模能力不能直接当作本机部署的容量。[OASIS 研究 v5](https://arxiv.org/abs/2411.11581v5)

Social Simulacra 将社区目标、规则和成员设定作为输入，生成社区互动原型，帮助设计者探索规则变化。这为“规则文本和社区设计的预演”提供了研究上的相邻依据，不能替代当前项目自己的效果评估。[Social Simulacra 原始研究](https://arxiv.org/abs/2208.04024v1)

Generative Agents 展示了包含记忆、规划与反思的交互式角色及可信行为，可作为沟通排练、交互原型和虚构角色应用的参考。行为看起来可信，与对现实行为具有预测效度，是不同评价目标。[Generative Agents 研究 v2](https://arxiv.org/abs/2304.03442v2)

基于 1,052 名参与者访谈与问卷的个人模拟研究，使用真实自报告数据和留出测评，并把指标与参与者自己的重测一致性比较。它说明可靠的人设依据和外部测量很重要；其结果不能迁移成 MiroFish 对任意未来事件的准确率。此处采用 2026 年 6 月修订的 v3，而非只沿用早期传播口径。[基于自报告的个人模拟研究 v3](https://arxiv.org/abs/2411.10109v3)

### 1.3 本报告的判断范围

下文的八类场景是拟议应用，没有在本机新增运行。优先级综合考虑当前讨论能力、材料能否形成可核验规则、结果能否由真实反馈检验、实施工作量以及误判后果，不是市场规模、收入潜力或成功概率排名。

## 2 适用场景筛选标准

一个场景适合先试点，通常需要同时回答以下问题：

1. **谁在互动？** 能列出角色、目标、责任和相互关系，而不只是年龄或身份标签。
2. **规则是什么？** 有可检查的原始文件、事实和约束，能区分既有事实、提案和未知项。
3. **为什么需要多角色？** 一个角色的回复会影响另一个角色的追问或立场，而非仅列出独立意见。
4. **要发现什么？** 目标是疑问、例外、误解、责任缺口或讨论素材；不强求模型直接给真实频率。
5. **如何检验价值？** 有业务专家、历史反馈或小范围真实试用，可以判断模拟提出的问题是否有效。

如果只需要总结材料和起草 FAQ，单次 LLM 问答可能更省事。如果关键结果由排队、资源、预算或物理约束决定，应先使用相应计算方法。多 Agent 不会自动弥补缺少事实或计算模型的问题。

## 3 应用场景与优先级

“可试点”表示可以开展问题发现型实验，不表示可以跳过真实业务验证。“需补齐”表示目标能力尚无当前完整工作流支持。

| 场景 | 当前最合适的用途 | 就绪判断 | 首批优先级 |
|---|---|---|---|
| 产品与服务规则变更 | 发现新规则的误解、例外和沟通缺口 | 材料与配置即可先试点 | 第一批 |
| 企业流程变更 | 发现责任边界、紧急情形和跨部门冲突 | 材料与配置即可先试点 | 第一批 |
| 客服争议与公告 | 预演追问、核对承诺、补充 FAQ | 材料与配置即可先试点 | 第一批 |
| 培训与教学复盘 | 提供角色互动案例和追问素材 | 观察与访谈可试点；完整真人演练需补齐 | 有培训目标时优先 |
| 社区平台治理 | 评审规则措辞、申诉条件与争议 | 文本评审可试点；自动处置机制需补齐 | 第二批 |
| 园区与项目多方协商 | 梳理条件性支持、责任与沟通议题 | 可先做讨论预演 | 第二批 |
| 群像与互动叙事创作 | 生成角色冲突、关系变化和剧情素材 | 文字素材可试点；游戏运行机制需补齐 | 创作需求明确时优先 |
| 供应链异常沟通 | 检查通知链、升级责任和承诺冲突 | 沟通可试点；定量运营模拟需补齐 | 定量需求明确后再扩展 |

若没有真实业务材料，培训和虚构创作更容易形成可启动输入；若已有产品文档、支持工单和真实反馈，前三项更适合验证业务价值。下面案例均为方法演示，不代表实际企业规则或故障。

## 4 产品与服务规则发布前评审

### 4.1 典型问题

一家团队文档服务准备把匿名共享链接的默认有效期从 30 天改为 7 天，管理员可以申请更长有效期。团队希望提前发现：用户是否理解已有链接如何处理、外部协作者会遇到什么问题、帮助文档是否遗漏紧急访问场景。

该任务以规则理解与角色互动为主，容易形成明确材料，也容易通过后续客服反馈验证。因此它是最优先的应用方向之一。

### 4.2 输入材料和角色

输入应包括旧规则、新规则、迁移安排、例外申请方式、已知故障与支持边界。使用授权、去标识后的历史问题作为角色依据，并把部分案例留出用于评估。

拟定角色可覆盖普通用户、团队管理员、外部协作者、项目负责人、客服、信息安全负责人和产品负责人。角色需要描述目标与权限，不应仅由“年轻用户”“企业用户”等宽泛标签决定行为。

### 4.3 两个可比较的方案

| 方案 | 唯一主要差异 | 观察问题 |
|---|---|---|
| A | 公告只说明默认有效期变为 7 天 | 是否误解既有链接会立即失效、是否不知道申请入口 |
| B | 在同样规则下补充迁移说明、入口和例外处理 | 这些疑问是否得到更明确的回应，是否产生新的执行问题 |

讨论结果可整理为用户疑问、被影响的工作流、FAQ 待补条目和材料中的歧义。模拟参与者说“不再使用”，只能视为生成的角色表达，不能直接换算为真实流失率。

### 4.4 如何验证价值

让不了解分组的产品与支持人员审核去重问题，检查是否对应真实机制、是否已在现有 FAQ 解决、是否值得修改发布材料。与同一材料上的“专家直接评审”和“单次 LLM 问答”比较新增有效问题及总审核时间。

上线后再对照真实咨询，判断预演命中了哪些问题、遗漏了哪些问题。预测真实咨询量或订阅转化，需要另外的数据与方法。

## 5 企业流程变更沟通

### 5.1 典型问题

一个项目团队要把需求变更从群聊口头确认改为工单审批，并要求影响评估。方案仍保留紧急处理通道，但对谁可以走紧急通道、何时补录、谁承担延期责任没有写清。

适合让产品、研发、测试、交付、销售、客户代表和流程负责人讨论。重点是暴露例外与责任冲突，而不是让模拟 Agent 实际办理工单。

### 5.2 输入与目标产物

| 输入 | 希望产出的结果 |
|---|---|
| 现行流程、拟议流程和真实角色职责 | 哪些步骤出现无人负责或多人重复负责 |
| 紧急变更与事后补录案例 | 例外条件、责任人及补录要求是否清晰 |
| 历史交付问题 | 讨论是否触及真实发生过的冲突 |
| 变更说明和培训材料 | 需要补充的解释、例子和问答 |

应只按组织中的职责构造角色，不用模拟给具体员工做绩效或胜任力判断。部门角色的生成观点，也不能当作该部门真实人员的意见。

### 5.3 适配价值和限制

本项目可以保存“客户要求临时变更—销售作出承诺—研发追问评估—交付担心延期”这样的讨论链，便于负责人回查冲突如何出现。这是多角色互动相对独立意见列表可能提供的增量价值，但仍需试点验证。

当前环境没有企业流程状态机、审批权限执行和 SLA 计时引擎。若目标是计算审批耗时、实际产能或流程吞吐，需要流程挖掘、业务系统数据或离散事件模拟支撑。

### 5.4 验证方法

请流程负责人核对每条“责任缺口”，用过去真实案例检查覆盖情况，再做一次小规模真实桌面评审。只有专家确认的缺口和可执行修改进入正式流程文档。

## 6 客户服务争议与公告演练

### 6.1 典型问题

虚构的在线服务发生中断。已知核心服务恢复，部分积压任务仍在处理，根因尚待确认，团队承诺在一小时后更新进展。需要检查公告是否让不同用户理解一致，以及客服会面临哪些追问。

角色可包括受影响用户、企业管理员、客服、运维、客户成功、合作伙伴和沟通负责人。

### 6.2 适合比较什么

比较两份只在解释与承诺上有区别的公告，例如一份含糊地写“已恢复”，另一份明确区分核心恢复、积压、未知根因、下一次更新时间和支持入口。应让两份材料都服从同一已知事实，不能靠给某组额外事实制造优势。

希望发现的问题包括：

- 用户能否区分功能恢复与积压任务完成。
- 客服是否被迫解释材料没有说明的事项。
- 运维与客户成功对外承诺是否冲突。
- 哪些回复把未知原因说成确定事实。
- 已约定的更新时间和反馈入口是否足够明确。

### 6.3 产物与验证

输出公告问题清单、追问分组、FAQ 草案和承诺核对表。用去标识的历史事件开展回测，再由服务负责人审核。

当前不接入实时舆情抓取，也不自动向外部平台发布公告。这一用途是内部演练，不能仅用点赞或生成情绪推断真实品牌损失，也不能把多角色模拟变成自动对外承诺。

## 7 其他五类应用场景

### 7.1 培训与教学复盘

**适合的任务：**为产品、客服、项目沟通或公共服务课程提供角色冲突案例，组织学员观察讨论、追问角色并复盘回应方式。

输入是教学目标、角色卡、已知事实和评价标准。输出是讨论片段、角色访谈、可追溯的分歧和教师提问素材。可让教师检查材料是否覆盖预定教学点，并在小范围课程中验证学员能否识别事实、推断和承诺。

当前可以观察模拟、在环境关闭前访谈并人工复盘。教师实时暂停、注入事件、让真人代替某个角色参与，以及课程成绩评价等，尚无完整产品工作流。系统不能仅凭学员或 Agent 的生成对话自动给人做能力判断。

### 7.2 社区平台治理规则设计

**适合的任务：**在用户社区、知识社区或二手交易社区推出发帖规范、申诉流程、广告限制前，检查措辞和例外条件。

例如规定交易帖子必须披露已知缺陷，成员可能追问“不确定算不算已知”“买家补充证据后怎么办”“误删后如何申诉”。输入可包含规则、真实争议的去标识摘要和管理员处理说明；角色覆盖新成员、长期成员、卖家、买家与管理员。

当前可以评审规则文本及成员对规则的理解。若要比较自动删帖、申诉时限、限流或真实审核算法的效果，则必须实现相应处置动作、状态和测量。只把规则写进提示词，不等于引擎已经严格执行了规则。

验证应结合真实管理员标注与有限范围的社区试用，衡量规则歧义和申诉缺口，而非推断真实违规率或封禁误伤率。

### 7.3 园区运营与项目多方协商

**适合的任务：**预演园区施工安排、共享会议室、停车时段或活动场地分配中的条件性支持与职责冲突。这是对已有共享阅读室能力较近的扩展。

角色可包括物业、租户、商户、员工代表、项目实施方和运营负责人。材料需要给出真实可行时段、权责、替代方案和不可变约束，产物是争议议题、责任交接及待澄清事项。

本项目可帮助梳理“谁愿意接受什么条件”，不能据此判断所有租户已经同意，也不能替代真实协商。涉及排期、容量、噪声测量等定量约束时，应先用相应实际数据或计算工具验证可行性。

### 7.4 群像创作与互动叙事素材

**适合的任务：**围绕虚构角色的公开背景、利益冲突和关系，生成不同立场的发言、冲突发展线索及人物访谈，辅助作者检查角色一致性。

输入可以是设定集、人物目标、关系和已有情节，输出是剧情素材与矛盾清单。验证者是作者或编辑，可按“是否违反设定”“是否有重复角色”“是否有新的可用冲突”评估，而不追求现实人口代表性。

当前环境依然以社交帖子和评论为主要交互。即时 NPC 控制、空间移动、物理状态、游戏数值、严格私有信息和剧情分支执行需另外实现。已有图谱记忆也不能自动保证人物秘密不会在生成上下文中泄露。因此适合文字素材预演，不宜宣称已经具备完整游戏世界模拟能力。

### 7.5 供应链异常沟通与责任交接

**适合的任务：**围绕虚构或脱敏的延期、缺货、供应商变更，检查销售、采购、生产、仓储、客户与客服的通知顺序、升级责任及对外承诺是否冲突。

输入应是已经核实的库存、交期约束、合同中的业务承诺摘要及沟通规则。产物是信息缺口、升级路径和需要补充的说明，不是库存计算结果。

真实缺货率、生产排程、运输延误概率和最优采购量依赖数量模型、业务数据及硬约束。本项目尚没有这些引擎。更合理的扩展是让定量模型给出可行状态，再让 MiroFish 分析沟通与协调问题；这个接口需要新增，不能当作已经完成的集成。

## 8 与其他方法的分工

| 方法 | 更适合解决什么 | MiroFish 的合理位置 |
|---|---|---|
| 单次 LLM 问答 | 总结、FAQ 初稿、独立问题清单 | 作为低成本基线，验证多角色互动是否真的增加价值 |
| 专家评审 | 规则解释、业务事实与可执行性判断 | 给模拟问题做最终核验，不被生成观点取代 |
| 真实访谈与问卷 | 真实用户如何理解、表达或选择 | 为角色提供依据，验证模拟发现，提供人口层面的观测 |
| 原型测试或真实小范围试用 | 用户在真实界面和约束下能否完成任务 | 判断规则或产品修改是否真的解决问题 |
| 流程挖掘、排队与离散事件模拟 | 等待时间、资源占用、吞吐等 | 提供定量状态，社交讨论不能替代它们 |
| 优化与预测模型 | 库存、排程、数值概率等 | 需要专门模型，不能把自然语言“推演”当作同类结果 |
| 多角色模拟 | 观察角色回应、误解、争议和条件性支持 | 形成供真实验证的问题假设与讨论证据 |

判断是否值得使用 MiroFish，应看它能否发现基线方法遗漏、且被专家确认有效的问题。若单次问答已经覆盖大部分有效问题，多 Agent 带来的成本和审核负担可能不值得。

## 9 试点设计与效果评估

### 9.1 从可验证目标开始

一个合适的试点问题是：

> 与专家直接评审和单次 LLM 问答相比，多角色模拟能否发现额外的规则歧义、真实例外和责任缺口，而且来源可核对、总审核负担可接受？

不应把“输出更长”“Agent 更多”“看起来像真实争论”作为主要成功标准。

### 9.2 建议的实验组织

1. 选一个规则清楚、结果可以由负责人审核的具体变更。
2. 固定一份事实材料，分别写两版仅改变一个关键因素的方案。
3. 把部分历史问题留出，不同时放入角色材料和评估答案，防止把答案复述当成发现。
4. 在同一材料上形成专家评审与单次 LLM 基线。
5. 使用 6～10 个角色、三轮作为首次探索配置；这是接近既有验收规模的起点，不是已验证的行业最优参数。
6. 可先每版运行三次，共六个独立 namespace，观察结果波动；这只是探索性重复，不支持可靠频率、显著性或因果效应估计。
7. 用统一标准去重和盲审问题，保存接受、拒绝及原因。
8. 若有价值，再做真实用户评审或小范围试用，决定是否扩展。

同一生成模型的多次运行仍有共同偏差，不能当作多批独立真实人样本。当前系统每次可能重新生成人设、本体和开场帖，两个项目之间的差异也可能来自这些变量。

低改造试点应记录并审核这些变化，将结果当作定性方案比较。严格可比较的实验需要角色模板、跨图映射、初始帖版本与实验 manifest 支持。不能未经验证地复制带旧图引用的人设文件，就宣称完成了严格 A/B 对照。

### 9.3 指标定义

| 指标 | 定义或检查方式 | 用途 |
|---|---|---|
| 有效问题占比 | 专家接受的去重问题数 / 全部提出的去重问题数 | 防止用大量低质量问题制造效果 |
| 历史问题覆盖率 | 命中的留出历史问题类目 / 留出类目总数 | 检查已知真实问题是否遗漏；不是未来准确率 |
| 新增有效问题数 | 模拟有效问题集合中，基线问题集合未覆盖的部分 | 测量多角色方法的增量 |
| 事实越界率 | 被当作确定事实表达、但材料不支持的断言 / 已审核事实断言 | 检查报告或角色是否编造规则；明确标记的假设另列 |
| 引用一致性 | 引文及归属与动作原文、平台和轮次一致的比例 | 判断报告来源是否可用 |
| 追溯完整性 | 被引用动作能否定位到原始日志与 trace | 使用本地改造的来源优势 |
| 角色有效性 | 角色是否覆盖业务利益、是否存在主体重复 | 防止用多个相似角色伪造观点多样性 |
| 总审核耗时 | 准备、运行观察、专家审核与修改的总时间 | 不能只计模型生成速度 |
| 实际业务验证 | 真实评审或试用是否确认并解决了某个问题 | 决定是否继续投入 |

技术层面必须核对所有应写回事件已确认、回执与图谱水位一致，并区分初始动作和自主动作。技术验收通过后，才有资格比较业务产物；36/36 水位本身不是业务效果指标。

### 9.4 通过与停止条件

出现下列情况时，保留该次结果并标为无效或需重做：只有初始帖而没有自主发言；关键角色重复或遗漏；材料规则被持续改写；记忆确认失败；报告主要结论找不到对应来源。

如果多次试点不能稳定产生基线之外的有效问题，或专家纠错耗时超过收益，应缩小范围或改用更简单的方法。各业务可在运行前约定具体通过标准，不应在看到结果后再调整标准使试点“通过”。

## 10 产品化与技术补齐路线

### 10.1 第一阶段 用现有能力验证交付物

早期可把交付目标定义成“方案发布前评审包”：输入材料和角色清单、问题与争议清单、相关原始动作、FAQ 或规则修改建议、未解决项及人工审核记录。

这一阶段优先增加可复用材料格式、事实/提案/未知项标签、角色审核表和报告问题结构。报告中的问题还需要人工归并，不能假设目前已有完整的结构化问题管理界面。

### 10.2 第二阶段 支持可比较的重复实验

| 补齐项 | 解决的问题 |
|---|---|
| 角色卡与初始配置模板 | 每次自动生成人设造成的变量漂移 |
| 角色到新图的显式映射 | 跨 namespace 复用输入时错误引用旧图 |
| 实验 manifest 与版本差异 | 无法判断两次运行究竟改变了什么 |
| 逐角色信息可见性与上下文控制 | 公共材料、内部信息和审核答案混入所有角色，造成过度知情 |
| 批量新图和结果归档 | 单图单次限制下重复实验的操作负担 |
| 问题去重、人工标签和基线比较 | 报告很长但难以判断新增价值 |
| 全链路调用与耗时统计 | 无法计算准备、OASIS、Graphiti、报告的完整成本 |

Graphiti 审计提供部分模型调用耗时和 usage，但不是整个链路的统一账单。总成本还包括其他模型调用、机器运行、准备、审核和维护，不能只根据这一个日志估计节省金额。

### 10.3 第三阶段 再做行业工作流和多人服务

社区治理可增加可执行的审核与申诉状态；企业流程可对接经核验的业务状态；供应链可对接定量引擎。每种扩展都应明确“引擎执行了规则”与“Agent 仅在文字里谈论规则”的差别。

在面向多人或外部客户提供服务前，还需补齐用户权限、业务数据归属、持久化准备/报告任务、调度限流和恢复演练。当前本机图 namespace 隔离、服务间 token 与 outbox，并不等于已经具备完整多租户产品。

本地单平台参数接线也有已知限制，试点使用已验收的 parallel 通道；三轮应显式使用 API 或运行页参数。参见[技术架构与主流程说明](MiroFish技术架构与主流程说明.md#17-验证结果与扩展边界)。

## 11 不宜直接承担的任务

| 任务 | 当前不适配的原因 | 可以保留的辅助用途 |
|---|---|---|
| 精确预测销量、流失率、市场规模 | 未建立代表性样本和结果校准 | 发现购买疑问、退出理由或待验证假设 |
| 用模拟问卷替代真实民意或客户调研 | 人设不是真实抽样，回复有共同模型偏差 | 设计访谈提纲、检查问题覆盖 |
| 自动决定具体人的招聘、绩效或资源资格 | 模拟角色观点不构成个人评价依据 | 对流程文字和一般例外开展评审 |
| 自动医疗、法律或投资结论 | 当前未建立相关领域的可靠决策流程 | 整理需要交由专业人员核验的问题 |
| 定量库存、交通、生产与物理过程优化 | 缺少数量状态、硬约束与对应计算引擎 | 对已验证方案做沟通预演 |
| 实时全网舆情与自动对外运营 | 无完整实时数据接入及外部发布工作流 | 在固定材料上进行内部公告演练 |
| 完整游戏世界与即时 NPC | 缺少空间、物理、游戏执行及严格私有状态 | 文字角色、冲突和剧情素材生成 |

这些边界不否定研究和扩展价值，而是限定当前版本可以直接交付什么，防止把生成叙事误当成已校准的业务结果。

## 12 首个试点建议与输入模板

### 12.1 优先选择什么

若你已经有产品或内部工具的变更文档，建议先试**产品规则发布前评审**。它便于限定问题，也有客服和真实试用作为后续验证来源。若没有产品材料但有成熟企业流程，则先做**流程例外与责任缺口评审**。两者都缺少时，可先做虚构培训案例验证操作与评价标准，不应立即承诺行业效果。

建议第一轮交付只回答三个问题：是否出现基线遗漏的有效问题；问题能否追溯并由业务负责人确认；准备和审核的总成本是否值得继续。通过后，再考虑更复杂的平台机制或定量引擎接入。

### 12.2 种子材料模板

以下为虚构产品案例的可替换格式，角色与规则需按真实业务填写：

```text
项目：团队文档共享链接规则预演
目标：发现公开规则中的误解、例外与支持需求。

公开背景：
某团队文档服务准备调整新建匿名共享链接的默认有效期。
当前公开规则默认30天，拟议规则默认7天。
此次讨论只评审规则和公告，不预测真实购买或流失。

本次提交的公开方案：
填写公告原文、办理入口、已明确的例外和支持边界。
对两版公告，分别创建项目，保持其他公开背景一致。

明确尚未决定的事项：
填写旧链接迁移、例外资格或其他尚未决定的问题。
这些是待澄清项，不允许把推测写成已经批准的规则。

参与角色：
普通用户：关心已有工作是否受影响。
团队管理员：关心设置、审批和团队支持成本。
外部协作者：关心链接失效后的访问方式。
项目负责人：关心交付与协作连续性。
客户支持人员：关心如何解释规则和处理例外。
产品负责人：负责解释本次已经公开的方案。
信息安全角色：关心公开共享的风险与边界。

材料边界：
只使用这里提供的公开背景和方案作为确定事实。
可能情况、假设和建议应明确标记，不能伪造已发生事实。
```

如果测试公告理解，共同种子尽量只放参与者确实可见的材料；内部完整真相和评估答案另存给审核者。当前没有可依赖的严格逐角色知识隔离，不能仅写“某角色不知道”就假设引擎一定隔离了该信息。需要精确模拟不同角色可见信息时，应先补齐相应机制。

### 12.3 模拟需求模板

```text
依据材料创建6至10个适合参与规则评审的角色。
角色类型使用Person、Organization或明确可配置的角色类型。
不得把产品、页面、地点或活动直接当作参与者。
在两个本地平台模拟最多3轮，启用图谱记忆写回。
观察角色对公告的追问、相互回应、例外诉求和责任冲突。
不要预设哪个方案一定更好，也不要输出真实支持率或流失率。
输出：
1. 材料明确事实、未决事项和生成假设的区分；
2. 去重的问题清单及对应角色；
3. 发生相互回应的讨论链与原始动作来源；
4. 建议补充的说明或FAQ；
5. 初始配置帖与自主动作的数量区别；
6. 仍需真实用户或业务负责人验证的事项。
```

提示词不能替代运行参数，也不能保证模型完全遵守所有约束。三轮上限应显式设置；新行业角色类型若不被默认规则识别，需要核对本体并配置筛选。具体操作与访谈关闭顺序见[操作手册](MiroFish操作手册.md)。
